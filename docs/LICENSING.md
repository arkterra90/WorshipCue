# Licensing implementation and operations

Priority 9 provides editing-only mode, Cloudflare-authoritative activation, five installation slots, signed seven-day offline leases, protected installation keys, and device transfer controls. Use **Settings → License Activation & Devices…** or **License…** in the status bar. User instructions ship in [offline Help](help/licensing.md).

## Deployment in this workspace

- Worker: `https://worshipcue-licensing.jerqin.workers.dev`
- D1 database: `worshipcue-licenses`; migrations `0001_licenses.sql` and `0002_idempotent_activation.sql` are applied.
- One real developer license was issued by this Worker. Its code is in the ignored `licensing/secrets/developer-license.json`, restricted to the local user. Do not paste it into source, logs, issues, or chat. This workstation has a remembered local activation.
- Worker secrets are stored in Cloudflare and backed up in ignored `licensing/secrets/worker-secrets.json` (mode 0600, directory 0700). Keep an encrypted backup. Never commit that directory or upload it as a build artifact.
- The public verification key in `licensing/public-key.txt` and API origin in CMake are public configuration. No private signing key, admin token, or Cloudflare token belongs in a desktop build.

## Protocol and authoritative state

The Worker uses Web Crypto Ed25519 signing and verification. A high-entropy license code is generated by `/admin/issue`; only `SHA-256(CODE_PEPPER + ':' + code)` is persisted. Random 256-bit codes make offline guessing impractical without requiring a slow password hash. D1 stores license status, fixed maximum activations of five, issuance/revocation times and reason, installation public keys and labels, activation/verification times, deactivation times, and short-lived used nonces. It does not store plaintext codes or desktop installation private keys.

Every desktop request contains an encoded JSON payload signed by its installation key. The signed fields include API path, public key, random nonce, timestamp, and operation-specific fields. Requests older/newer than five minutes are rejected. The outer fields must agree with the signed payload. Installation IDs are SHA-256 of the public key. The activation request additionally proves possession of the license code; subsequent requests prove possession of the registered installation key.

Nonce consumption and writes share a D1 batch transaction. SQL triggers enforce the five-active-installation limit inside the write, including reactivation. An UPSERT makes simultaneous registrations of the same installation idempotent. No client-provided count is trusted. Requests use primary-consistent D1 sessions and recheck status inside the transaction. Nonces expire after ten minutes, when the signed request timestamp is already invalid.

Routes (all HTTPS POST with bounded JSON bodies):

| Route | Purpose |
| --- | --- |
| `/v1/activate` | Register/reactivate the signed installation using its license code; return lease and active devices |
| `/v1/verify` | Verify active license and installation; renew lease |
| `/v1/devices` | Refresh device list and authorization |
| `/v1/deactivate` | Release this installation |
| `/v1/release` | An active installation releases another installation on the same license |
| `/admin/issue` | Issue a random credential; requires the separate admin bearer secret and fresh nonce |
| `/admin/revoke` | Revoke a license with a reason; requires admin authentication and fresh nonce |

The lease is `base64url(payload).base64url(Ed25519 signature over encoded payload)`. Claims include version 1, audience `worshipcue-live`, license ID, installation ID, active status, issuance time, and expiry no more than seven days later. Qt verifies the signature and every relevant claim with OpenSSL. TLS certificate checks remain enabled; redirects are refused. Network requests have a 15-second timeout and bounded response size. Only safe fixed error messages reach the UI; requests, credentials, and exception internals are not logged.

Cloudflare rate limiting is configured at 30 requests per IP per minute. These counters are per Cloudflare location, not a strict global quota. Enable account-level WAF/abuse monitoring as needed, particularly before public distribution. Worker observability is disabled to avoid automatic request capture. Protect admin routes further with Cloudflare Access and service tokens if operating a larger issuance system; adapt the private administration script to supply those headers. No issuance/admin capability is exposed through MCP or the desktop UI.

See the official [Workers Web Crypto API](https://developers.cloudflare.com/workers/runtime-apis/web-crypto/), [D1 batch API](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch), and [rate-limit binding documentation](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/).

## Desktop authorization and storage

`LicenseManager` loads OS-protected state at startup, verifies cached authorization, and attempts online verification. Successful checks renew daily. Outages preserve valid leases and retry hourly; invalid/expired authorization retries every five minutes. Manual refresh is available. Authorization is checked when taking/navigating cues, sending MIDI, routing outputs, showing display windows, painting live windows, and controlling live media. A 30-second watchdog clears live state, stops media through the existing shared transport, releases held MIDI notes, hides all outputs, and restores physical display modes when authorization becomes invalid. Saved routes and edit data survive. Explicit server denials clear the lease and persist the denial.

macOS saves the installation seed, signed lease, machine-binding hash, denial state, and clock high-water mark together under `AppLocalDataLocation/licensing/activation-state.bin`. The directory is owner-only (0700), the file is owner-only (0600), and replacement is atomic. AES-256-GCM authenticates/encrypts the cache using a key derived from a domain separator, Qt's machine unique ID, and the current OS user ID. No password, Keychain unlock, or application-signature approval is needed to reopen it, so unsigned updates also preserve activation. Encryption binds a copied cache to its original computer/user and rejects ordinary tampering. The identifiers used for derivation are not confidential: OS file permissions and the current user are the local trust boundary, not a claim of protection against hostile code running as that user. The server signature, expiry and installation registration remain authoritative for authorization.

Windows retains user-scope DPAPI with `CRYPTPROTECT_UI_FORBIDDEN` and atomic storage as `license.dpapi`. Windows native validation is still pending. Neither platform stores the master license code after activation or relies on a locally editable authorization Boolean.

For older macOS installations, a missing cache triggers a best-effort read of the legacy Keychain item (`org.worshipcue.desktop.license`, account `installation-v1`). Legacy Keychain interaction is explicitly disabled for that read and restored afterward, because `kSecUseAuthenticationUIFail` alone applies only to the Data Protection Keychain. An already-authorized read migrates the installation unchanged; a denied/locked read is skipped without showing a dialog or blocking the editor. In that case the user enters their activation code once and can release the old registration. Once the private file exists, startup, renewal and deactivation never access Keychain. The legacy item is left intact for older builds; the updated client always prefers the new file.

A SHA-256 binding of Qt's machine unique ID stays inside protected local state; it is never sent to Cloudflare. The server sees a random public-key-based installation ID and the user-supplied name. Library copying does not transfer authorization. Reinstall with preserved protected state reuses the slot; a wiped profile, removed activation/DPAPI state, different OS user, or hardware change may require a new slot. Release the old installation from another active machine. An administrator can revoke a lost license and issue a replacement if no active installation survives. Recovery of corrupt protected state requires removing only that activation file/OS credential after releasing/replacing the old activation; do not delete the library.

The protected high-water mark and monotonic runtime clock reject practical clock rollback. Client software remains modifiable by its owner, and privileged extraction/tampering cannot be made impossible. Revocation and remote release cannot invalidate an already-issued offline lease immediately: the maximum delay is seven days, plus up to 30 seconds for an idle output watchdog. Remote release can temporarily leave an old offline lease alongside the five currently registered slots. Local deactivation clears authorization immediately after the server confirms it. A lost deactivation response retains cached authorization until verification reports the server-side removal; retry Verify to resolve it.

Editor previews, media inspection dialogs, stage layout design, and output configuration remain available without a license; they do not route live service content to external output windows. Live MIDI output and mapped live controls require authorization; releasing already-held notes remains possible to avoid stuck notes. The MCP companion remains editor-only and cannot activate licenses or take slides live.

## Reproduce deployment

The checked-in Wrangler configuration targets the existing Worker/database. For a separate environment, copy it and substitute a new Worker name and D1 ID before deploying; create a separate authority and never overwrite the existing production secrets accidentally.

```sh
cd licensing
npm ci
npm test
# New environments only; the current deployment already has these resources.
npx wrangler login
npx wrangler d1 create worshipcue-licenses
# Put its database_id in your environment's Wrangler configuration.
npx wrangler d1 migrations apply worshipcue-licenses --remote
node provision-secrets.mjs
npx wrangler deploy
npx wrangler secret bulk secrets/worker-secrets.json
```

The secret generator refuses to overwrite existing files. Upload secrets only to the intended Worker/account. The Worker fails closed before secrets are installed. Copy only `secrets/public-key.txt` into the public verification-key file for a new authority. Configure the desktop with the matching HTTPS origin and public key:

```sh
cmake -S . -B build-local \
  -DWORSHIPCUE_LICENSE_URL=https://YOUR_WORKER_HOST \
  -DWORSHIPCUE_LICENSE_PUBLIC_KEY=YOUR_PUBLIC_BASE64URL_KEY
cmake --build build-local --target WorshipCue
```

macOS development dependencies now include `openssl@3` alongside CMake and Qt. Supply `-DOPENSSL_ROOT_DIR=/opt/homebrew/opt/openssl@3` if discovery needs help. Windows needs Qt and an OpenSSL Crypto development package compatible with its compiler. Bundling OpenSSL with Qt, installer signing, and clean-machine distribution checks belong to Priority 10.

Issue the developer license **once** against the actual deployed backend:

```sh
node licensing/admin.mjs issue https://YOUR_WORKER_HOST
```

The script writes `licensing/secrets/developer-license.json` with mode 0600 and refuses to issue another when that output already exists. `revoke HTTPS_ORIGIN LICENSE_ID REASON` records revocation. Protect the admin bearer token like the signing key. Rotation of `ADMIN_TOKEN` does not invalidate leases; rotating `CODE_PEPPER` invalidates existing code verifiers unless migrated. Signing-key rotation requires coordinated public-key delivery/new leases; do not casually replace it. D1 Time Travel/backups and an encrypted secret backup are necessary for disaster recovery.

## Validation and checks

```sh
node --test licensing/test/*.test.mjs
cmake -S . -B build-priority9 -DWORSHIPCUE_BUILD_TESTS=ON
cmake --build build-priority9 --parallel 4
ctest --test-dir build-priority9 --output-on-failure
```

Node tests run the actual Worker handler/Web Crypto and production migrations through a real SQLite-backed D1 test adapter. The five test groups cover malformed signed envelopes, concurrent sixth attempts, simultaneous duplicate registrations at the cap, invalid credentials, stale/tampered/replayed requests, transfer, remote release, revocation, verifier-only persistence, HTTPS, admin authentication, body bounds, and rate limits. Qt tests cover invalid/expired/revoked/copied leases, mismatched authorities/claims, rollback, protected denial state, unavailable storage, editing-only library/UI behavior, all four denied outputs, and live-controller enforcement. Existing operator/output tests use ephemeral test authorities and in-memory stores; those keys cannot authorize a production build.

Opt-in real-service checks use private local files and the real platform activation store. They are excluded from the normal build/test run:

```sh
cmake --build build-priority9 --target WorshipCueLicenseCheck
build-priority9/WorshipCueLicenseCheck --activate-file licensing/secrets/developer-license.json
build-priority9/WorshipCueLicenseCheck --verify
# Explicitly release this workstation if desired:
build-priority9/WorshipCueLicenseCheck --deactivate
# Creates and cleans up temporary activations on the developer license:
node licensing/live-check.mjs https://YOUR_WORKER_HOST
```

The live check verified the actual Worker/D1 five-machine limit under concurrent requests, same-installation reuse, renewal, deactivation, and transfer, then released its temporary activations. The Qt integration check verified actual native activation and persistence. Passwordless native checks verify launch from the encrypted macOS cache. The licensing dialog was visually reviewed with the real licensed workstation and active-device row. Physical multi-screen behavior and Windows DPAPI/runtime still require their native environments. Do not claim signed installer readiness from these checks.


The remembered-activation follow-up was checked with real native activation and fresh-process verification without OS authentication, owner-only encrypted persistence tests, and the rebuilt installed-DMG probe. A locked macOS desktop prevented a full native focus/media regression pass during that follow-up; those two suites still require an unlocked session. The licensing, packaging and noninteractive suites passed. No local library schema or server protocol change was required.
